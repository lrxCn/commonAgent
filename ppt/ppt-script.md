## Slide 7 — Agent 单轮流水线

**时长**：2分钟

**幻灯片内容**：

```
用户消息
   │
   ▼
入站护栏 ──→ 拦截非法输入
   │
   ▼
加载记忆 + 意图分类
   │
   ├──→ 寒暄/记忆查询/事实写入 → 快速路径（跳过RAG和Supervisor）
   │
   ▼
Query改写 → RAG路由 → 知识检索
   │
   ▼
上下文组装（记忆+知识+工具+消息，受预算管控）
   │
   ▼
Supervisor（deepagents）──→ 文本回复 或 客户端工具动作
   │
   ▼
出站护栏 → 异步记忆写入 → 返回用户
```

**台词**：
> 这是Agent处理一轮对话的完整流水线。用户消息进来后，先过入站护栏做安全检查；然后加载记忆并做意图分类——这里我们的控制面是纯确定性的规则引擎，不调LLM，速度快；根据意图走不同的路径：如果是寒暄、记忆查询或事实写入，走快速路径直接响应，不需要过RAG和大模型；如果是正常问答或工具调用，会先做Query改写、RAG检索、上下文组装，然后交给Supervisor决策；最后过出站护栏，异步写入记忆，返回用户。整个过程中，上下文预算管理器会动态裁剪各部分的token占比，防止窗口溢出。

## Slide 8 — 核心技术选型

**时长**：1分钟

**布局**：表格或卡片式，每项技术配一句选型理由

**幻灯片内容**：

```
| 组件          | 选型                   | 理由                           |
|--------------|------------------------|-------------------------------|
| Agent框架     | LangGraph + deepagents | 原生状态图、human-in-the-loop    |
| 语言          | Python                 | AI生态最成熟，库最丰富             |
| 对话持久化     | Postgres Checkpointer  | 生产级可靠性，与Store共用基础设施    |
| 长期记忆       | LangGraph Store+langmem| pgvector语义检索，结构化+推断双轨   |
| 知识库RAG     | Qdrant                 | 高性能向量检索，支持payload过滤     |
| 可观测性       | LangSmith              | trace、评测、数据集一体化          |
```

**台词**：
> 技术选型上，Agent框架选了LangGraph加deepagents，因为它原生支持状态图编排和human-in-the-loop，而且deepagents自带的规划和子Agent能力可以直接复用，不重复造轮子。长期记忆用LangGraph Store加langmem，支持结构化的用户画像和推断式自由文本记忆的双轨写入，底层都是Postgres加pgvector，运维成本低。知识库RAG用Qdrant，它的payload过滤能力让我们可以实现按角色隔离检索。

**幻灯片内容**：

```
接入三步走：

① 定义工具（Tool Description）
   业务方只需编写JSON描述：工具名、功能说明、参数Schema
   → Back自动注入工具白名单

② 实现工具（Client Action）
   Agent返回结构化的client_actions
   前端执行：页面跳转、表单提交、数据查询

③ 管理知识（RAG）
   管理员上传文档并绑定角色
   Agent自动切分、向量化、按角色隔离检索

业务方不改Agent代码，不碰LLM，不写Prompt
```

**台词**：
> 这是我们最看重的一点——业务方的接入成本要尽可能低。整个接入分三步：第一步，定义工具，业务方只需写一个JSON描述文件，说明工具名、功能和参数，Back会自动根据用户角色注入工具白名单；第二步，实现工具，Agent不直接调用业务API，而是返回结构化的client_actions，由前端执行页面跳转、表单提交等操作；第三步，管理知识，管理员在后台上传文档并绑定角色，Agent自动处理切分、向量化和检索。全程业务方不需要改Agent代码，不碰LLM，不写Prompt。

## Slide 12 — 落地障碍：私有化部署成本

**时长**：1分钟

**布局**：左侧"问题"，右侧"破局思路"

**幻灯片内容**：

```
拦路虎：动辄百万的GPU算力成本

破局思路：
技术侧
  → 优化Agent架构，减少不必要的LLM调用
  → 快速路径分流：寒暄/记忆/事实写入 不过大模型
```

**台词**：

## Slide 13 — 最大的机会：专业领域数据壁垒

**时长**：1分30秒

**布局**：上方一个核心观点，下方用类比图示（农业 → 通信）

**幻灯片内容**：

```
通用大模型发展逼近瓶颈 → 互联网公开数据快被"吃光了"
专业通信领域 → 高质量训练数据还没有被挖掘使用

破局路径：联邦学习 / 端侧训练
  客户机房本地数据微调 → 只带回"变聪明的模型权重"
  → 构建具备行业壁垒的通信大模型
```

**台词**：
> 最大的机会是什么？分享一个我之前的经历。我做过智慧农业，美国大农场50年前就开始积累土壤、种子、气候数据，而我们想发展智慧农业，卡脖子的第一关就是没有高质量历史数据。换到专业通信领域，情况相似。当前通用大模型发展已经逼近瓶颈，因为互联网上的公开数据快被"吃光了"。但在专业通信这个垂直领域，高质量的训练数据还没有被挖掘使用。如果我们能采用类似联邦学习的模式——在客户机房利用本地数据微调，训练后只把变聪明的模型权重带回来——我们就能利用独有的专业领域数据，构建真正具备行业壁垒的通信大模型。
